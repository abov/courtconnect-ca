# 2026-10-23 Load time on a throttled phone connection (measure only)

**Verdict: fine for the friends beta; nothing worth fixing yet.** The link speed, not the load order, sets the time, and the only real lever is sending fewer bytes. No app code changed.

## How it was measured
Live site https://abov.github.io/courtconnect-ca/ (read-only), headless Chrome driven over the DevTools protocol with real throttling: `Network.emulateNetworkConditions` (Slow 4G = 1.6 Mbps down, 150 ms RTT; Fast 3G = 1.6 Mbps, 562 ms RTT) plus 4x CPU slowdown, 390x844 mobile viewport, fresh profile for "cold", a second visit in the same profile for "warm". One run per condition (two slow-4G runs agreed within 0.1 s on the list time). Caveat: software WebGL on a desktop CPU, so pin times on a real phone GPU are probably a bit lower.

## Numbers
- **Sizes on the wire (gzip; GitHub Pages sends no brotli):** `venues.json` 2.43 MB -> 421 KB (17%); `index.html` 128 KB -> 38 KB; maplibre js 211 KB + css 9 KB (unpkg, cached for a year); `places.json` 21 KB and `zips.json` 15 KB (fetched only on first search); outline 0.7 KB; basemap style 5 KB plus about 18 sprite/font/raster tiles from openfreemap.
- **Cache:** `venues.json` has a weak ETag and `max-age=600`; `no-cache` makes the warm visit a conditional GET that returns **304, about 300 bytes**, costing one round trip (180 ms on Slow 4G, 615 ms on Fast 3G). Cheap; no need to change it.
- **Parse:** `JSON.parse` of the 2.4 MB (10,277 venues) takes 12 ms on this desktop and about 100-140 ms at 4x CPU. Not a problem.
- **Time to usable** (list = spinner gone, list and filters shown; pins = venue pins drawn; times from navigation start):

  - No throttle, cold: list 0.4 s, pins 1.7 s
  - Slow 4G, cold: list 4.9 s, pins 9.1 s, basemap done 17.6 s; warm: 1.8 s / 4.3 s / 4.6 s
  - Fast 3G, cold: list 6.6 s, pins 12.0 s, basemap done 19.6 s; warm: 2.2 s / 5.0 s / 5.3 s

## What actually costs time (Slow 4G, cold)
The page loads in a chain: HTML, then maplibre js (done at 1.5 s), then the `venues.json` fetch (1.6 s to 4.0 s), then the basemap style request (4.8 s), then pins draw (9.1 s). But the link is the limit, not the chain: 38 KB page + 220 KB maplibre + 421 KB data is about 3.3 s of a 1.6 Mbps link whatever the order, and pins then share it with the raster basemap tiles.

## Options, ranked (change nothing until the beta says it matters)
1. **Fewer bytes on the first load** is the only lever that scales on a bandwidth-limited link (option 3 below). The data file is 421 KB of the roughly 700 KB first load; maplibre (211 KB) cannot shrink.
2. **Start the data fetch in `<head>` and create the map before the data arrives** (tried, branch `perf/parallel-load`, local only, not a PR). I first expected about 1.3 s sooner for the list and 2-3 s for pins, but that was wrong: overlapping downloads share the same 1.6 Mbps, so the list does not come earlier. A local A/B (same files served gzipped from localhost, same throttle, live unpkg and basemap) was too noisy to prove anything: Slow 4G cold pins 8.6 s -> 7.8 s in one run, 8.8 s -> 12.4 s in another, list 4.7 -> 5.3 s and 5.1 -> 11.3 s. Not shipped; it is not worth the boot-order risk without a clear gain.
3. **Drop popup-only keys from the first file** and load them on first popup: address group `a/ai/ad/ap/ns/al` 59 KB gz, `ru` 17 KB, `ac` 9 KB (list uses only `ac` as a badge flag; could ship a bit), so about 85 KB gz (20%) -> 0.4 s on Slow 4G cold. Walls, events and sport blurbs (31 KB gz together) could load only when those views open: another 0.15 s. Costs a second file and a loading state in popups; worth it only if beta users on cell data complain.
4. **Not worth it:** shortening the 10-hex ids (`i`, 87 KB gz, 21%, but breaks every shared `#venue=` link); relying on the ETag/`max-age` instead of `no-cache` (saves one round trip, risks 10 minutes of stale data); a CDN with brotli (estimated 10-15% smaller than gzip, not measured, host change for little).

Next: nothing before the beta. If beta users on cell data report slow loads, do option 3 (smaller first file) and measure with several runs per condition, since a single run varies by several seconds on the live CDN and basemap.
