How CourtConnect is built

Open data in, a tested warehouse in the middle, one static file out, and gates that decide what ships. Everything here is measured or marked as not yet measured.

From source to map

  1. Open and public sources

    OpenStreetMap (OSM) knows where courts are. Overture Maps knows business names and addresses. US Census boundaries fill in cities. Hand-checked seed files add what no dataset knows, each with an evidence link and a date.

    Gate: public pages and open data only. No Google Places data, no one's logged-in accounts.

  2. Ingest (Python)

    Extract and load scripts land the raw data untouched. The Overture files are queried in place on S3, so a laptop fetches about 2% of the themes it reads.

    Gate: the loader refuses to shrink a table by more than 10%.

  3. Transform (dbt on DuckDB)

    Staging cleans each source. Intermediate models build a proximity graph, cluster courts into venues and match Overture places to them. Core and mart models are what the export reads.

    Gate: dbt tests (clusters converge, every court has one venue, confirmed venues need evidence) and a gold set that scores the matcher.

  4. Export

    One JSON file of about 2.4 MB, with a data dictionary and an llms.txt so people and AI tools can read it.

    Gate: CI fails if the committed export is stale.

  5. Serve

    A static MapLibre page on GitHub Pages. No server, no accounts, no bookings or payments. Location for “Near me” stays in the browser.

    Gate: CI builds on a small fixture dataset and never calls a live source.

  6. Refresh, twice a month

    A written runbook, plus scheduled agent runs that read public pages and open pull requests with evidence. A deterministic gate script, not a model, decides whether a routine refresh PR may merge itself. That switch was turned on on 2026-10-25 and has merged one PR so far (a routine refresh on 2026-10-25); everything else is merged by a person.

    Gate: tests, freshness limits, a scorecard that must not regress, a cap on how much a change may touch, and evidence on every row.

Decisions worth reading

  • ADR 0003: turn individual courts into venues by distance, and accept some wrong merges and splits.
  • ADR 0007: honesty over polish. Every claim says how we know it, and inferred means inferred.
  • ADR 0005: what was left out on purpose (Google Places) and why.
  • ADR 0018: kept SQL portable across two engines, then retired the second when nothing ran on it.
  • ADR 0017 and ADR 0019: models suggest, code and people decide, and when an agent may merge.

What is not done or not measured yet

  • Usage and friend feedback: a beta round is planned for December. No visitor numbers are quoted until they exist.
  • The LLM page reader is built but has not been run at scale, and the aerial-imagery pilot was dropped after it found no new venues.
  • Names are the weak spot: most OSM courts are unnamed, so many pins carry a name inferred from the park or school and are labelled that way.
